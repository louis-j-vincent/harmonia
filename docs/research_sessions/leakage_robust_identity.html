Leakage-robust chord identity: does a directional delta beat mean-pool?

Research session 2026-07-24 · POP909 · screen-before-build · every number from a real run

V0 mean-pool   V1 clip-pool   V2 root-normalised directional delta

Verdict — NULL for V2 (delta); the surviving lever is V1 clip-pool

The root-normalised directional delta is not a real complementary identity signal worth building into FusionChordDecoder. It wins only in the idealised regime its cancellation premise assumes — perfect GT boundaries + a clean linear common-mode contamination — where on synthetic MIDI it is the only feature immune to leakage (Panels A/B). On real audio-derived NNLS chroma, where boundaries jitter and leakage is nonlinear (harmonics, attack smear), it collapses to 0.42 vs mean-pool's ~0.90 (Panel C) — it degrades exactly like the 5 dead adjudicators. The diagnosis still holds (mean-pool's residual errors are 39% at ±P5 on real audio too), but the delta is the wrong cure. Per the brief's own gate, the real-audio transfer screen falsified the premise, so no head was trained — that would only fit a non-transferable signal.

The screen, in one sentence

Under contamination a leakage-robust feature does beat V0 mean-pool on root interval in the micro-segment regime, and the gap widens with contamination (V2−V0 goes from −14pp clean to +12pp at s=1.0; V2 even beats clip-pool V1 by +4pp there). But two facts kill it as a build target: (1) the whole effect vanishes once the pooling window is ≥0.4 s — the real pipeline's per-beat decode already pools far more than a micro-segment; (2) it does not survive contact with real audio. V2 also never helps quality (real-audio quality 0.46 vs V0/V1 0.73).

Method (reuse, don't reinvent)

  • Data — POP909 MIDI-derived per-frame chroma (pretty_midi piano-roll → bass/treble 12-pc halves @50 Hz), so GT boundaries/labels are TRULY perfect and contamination is the only knob. Real-audio arm reuses the 41 cached NNLS bothchroma features already on disk (data/cache/nnls_infer/) — no render, no disk cost. Boundaries/labels from harmonia.data.pop909_parser (functional root; /bass discarded → root+quality only).
  • V0 mean-pool anchored at the boundary + pre-boundary bleed (beat-snap register). V1 clip-pool strictly [t0,t0+W) (reuses the _clip_pool framing from yt_chord_corpus.py). V2 L1-normalised next-window minus prev-window, root-normalised to prev-root, conditioned on prev quality — window-independent.
  • Contamination (frame-level, shared by all variants): exp-decaying prev-chord sustain into early frames + beat-snap neighbour bleed + per-frame dropout/noise. It reproduces the documented confound: V0's residual root errors concentrate at ±P5 (~28–39%), matching the brief's "P4/P5 = 37% of root loss".
  • Screen — cosine kNN (k=25), song-disjoint splits, multi-seed; predict target = (interval=(next−prev root) mod 12, reduced quality). No training.

Honesty caveats

  • On clean chroma the delta is trivial (Δ=N−P recovers N given P), so only the contamination / transfer curves are informative — reported in full, including where V2 loses.
  • The synthetic contamination is a linear mix of the prev-chord profile — exactly the common-mode a linear delta cancels. That is why V2 looks robust on MIDI and is precisely why the real-audio arm is the load-bearing test: real leakage is not linear common-mode.
  • V2's clean-MIDI number is depressed by sparse MIDI boundary windows (kNN, not a trained head); this does not change the transfer conclusion (a head cannot recover information that boundary jitter destroys).

If you build anything: the surviving finding

The one leakage-robust lever that survives real audio is clip-pool (V1) — strictly post-boundary framing, which the repo already ships (seg_feature_clipped / _clip_pool). It edges V0 by ~5–8pp only in the short-window regime and is essentially tied at production window lengths. FusionChordDecoder emission hook (for the record, not implemented): harmonia/align/inference.py::viterbi_decode exposes a swappable per-beat EMISSION factor; the acoustically-grounded transition factor the brief wanted would go there. V2 does not earn that slot. Note the repo's ready transition priors (build_transition fifth-motion; the chord_progression_model.npz trigram) make fifth-motion cheap and would reinforce the P4/P5 error — so the P5 confusion is best attacked in the emission/feature, not the transition.
